## The hard part is keeping a project coherent

Ask an AI coding agent to add a feature and it can produce a convincing first draft quickly. The harder question comes a week later: can another person or agent understand that feature, change it safely, and follow the same conventions in the next part of the application?

That question has become familiar to teams building with TypeScript. A project can have a typed API, a separate job runner, a storage layer, an email provider, and a growing set of integrations. Each piece may work well on its own. The seams between them still ask developers to repeat setup, translate types, and explain local conventions over and over.

Igniter.js grew from working through those seams. The goal is a backend foundation with clear boundaries and repeatable patterns: define a typed API, add only the capabilities a project needs, and give people and coding agents a codebase they can inspect and extend with confidence.

That last part matters. AI assistance should make developers more effective while leaving architecture, security decisions, and review in human hands. Igniter.js is built around that collaboration: explicit APIs for the code, useful context for the agent, and a developer who stays responsible for the outcome.

## What Igniter.js brings together

Igniter.js is a TypeScript ecosystem organized around one foundation and a set of focused packages. Across the packages, you will find explicit inputs, typed contracts, focused guides, and builder APIs where they fit the package’s job. A project can adopt one package or connect several as its needs grow.

The foundation starts with `@igniter-js/core`. Core provides the application builder, typed context, controllers, queries, mutations, procedures, and router. Schemas can validate request data at runtime while TypeScript carries input and response types through the application. The result is a clear place to define the HTTP surface and the services each action can use.

Here is a small API built with the current Core API:

```typescript
import { Igniter } from '@igniter-js/core'
import { z } from 'zod'

type User = { id: string; name: string }

const users = new Map<string, User>()

const igniter = Igniter.create()
  .withContext({ users })
  .withConfig({ basePATH: '/api/v1' })
  .build()

const usersController = igniter.controller({
  name: 'users',
  path: '/users',
  actions: {
    list: igniter.query({
      path: '/',
      handler: async ({ context, response }) =>
        response.success({ users: [...context.users.values()] }),
    }),
    create: igniter.mutation({
      path: '/',
      method: 'POST',
      body: z.object({ name: z.string().min(1) }),
      handler: async ({ context, request, response }) => {
        const user = { id: crypto.randomUUID(), name: request.body.name }
        context.users.set(user.id, user)
        return response.created({ user })
      },
    }),
  },
})

const router = igniter.router.create()
  .addController('users', usersController)
  .withHealthCheck('/health')
  .build()

await router.listen(3000)
```

The API is available under `/api/v1/users`; the health check is under `/api/v1/health`. This example uses an in-memory map to keep the flow visible. A real application can place its database and other dependencies in the typed context and choose the runtime integration that fits its deployment.

## Start from the project you need

The CLI turns the first setup into an interactive flow. Run:

```bash
npx @igniter-js/cli@latest init my-igniter-app
```

The initializer asks you to choose a starter, optional add-ons, and a package manager. Depending on the selected add-ons, it can also ask about database options and Docker services. It then offers to initialize Git and install dependencies. When the target directory already contains files, the CLI asks whether to use a starter or install Igniter.js into the existing project.

The executable is named `igniter`. After setup, the CLI also provides development and generation commands for common project tasks. The exact files depend on the selected starter and add-ons, so use the generated project and the matching package guides as the source of truth. The Core [quick start](/docs/core/quick-start) walks through the API builder and router in detail.

## A package for each part of the application

The ecosystem is broad because backend applications have different needs. These packages fit together, but a project does not need to install every one of them.

| Package | Role in an application |
| --- | --- |
| [`@igniter-js/core`](/docs/core) | Typed HTTP APIs, request context, controllers, actions, procedures, and routing. |
| [`@igniter-js/caller`](/docs/caller) | A Fetch-based HTTP client with typed schemas, optional runtime validation, caching, retries, interceptors, and telemetry. |
| [`@igniter-js/app`](/docs/app) | A React application shell that connects an Igniter client to pages, loaders, shared context, state, triggers, and forms. |
| [`@igniter-js/common`](/docs/common) | Shared errors and TypeScript contracts for loggers and schema validators. |
| [`@igniter-js/store`](/docs/store) | Key-value operations, counters, claims, batches, typed events, streams, and scoped keys. |
| [`@igniter-js/jobs`](/docs/jobs) | Typed job definitions, dispatch and scheduling, workers, scopes, lifecycle hooks, and job events. |
| [`@igniter-js/collections`](/docs/collections) | Schema-driven content collections for structured data, with querying, hooks, validation, and events. |
| [`@igniter-js/storage`](/docs/storage) | Scoped file operations such as upload, list, read, copy, move, and delete, with policies and provider integrations. |
| [`@igniter-js/mail`](/docs/mail) | Typed transactional email templates, provider integrations, and optional queued delivery. |
| [`@igniter-js/bot`](/docs/bots) | Commands, middleware, sessions, and a shared bot API across chat platforms. |
| [`@igniter-js/agents`](/docs/agents) | Typed tools and toolsets, agent execution, memory, lifecycle hooks, and multi-agent coordination. |
| [`@igniter-js/connectors`](/docs/connectors) | Scoped third-party connections, actions, OAuth flows, webhooks, credential handling, and events. |
| [`@igniter-js/logger`](/docs/logger) | Structured logs, context, child loggers, log levels, and console, file, or HTTP transports. |
| [`@igniter-js/telemetry`](/docs/telemetry) | Structured event registries, session context, sampling, redaction, and transport fan-out. |
| [`@igniter-js/adapter-mcp-server`](/docs/mcp-server) | An adapter that exposes an Igniter router’s actions as MCP tools, with support for custom tools and related MCP capabilities. |

The [documentation index](/docs) groups each library around the same path: get started, learn the core concepts, follow focused guides, explore advanced behavior, and consult the API reference. Package-specific installation and runtime requirements live in those guides, where they can stay current as each library evolves.

The CLI is the companion to this runtime ecosystem. `@igniter-js/cli` creates a project with `igniter init` and includes development and generation commands for common tasks. It helps establish a starting structure; the application still owns its product decisions, dependencies, and deployment configuration.

## Follow one feature across the system

Imagine a team building a workspace product. A member submits an invitation through a Core action. The action validates the request, checks that the current user can invite someone to that workspace, and writes the invitation through the application’s persistence layer. It then dispatches a job rather than waiting for email delivery to finish before returning the HTTP response.

The job receives a typed invitation identifier. Its worker can reload the latest record, render the right message through Mail, and report success or failure through lifecycle hooks. If the invitation includes an uploaded file, Storage can enforce a path scope and upload policy. If the workspace connects to another service, Connectors can keep that credential and its actions within the workspace scope. Logger and Telemetry can add operational context without changing the request’s public shape.

This is a composition example, not an automatic workflow supplied by one command. Each package handles a boundary, and the application decides how the boundaries fit its business rules. A small product can begin with Core and add Mail. A multi-tenant service may later add Jobs, Store, Connectors, and Telemetry. The shape of the code can grow with the product instead of requiring the team to adopt the full catalog on day one.

## Keep contracts useful as the application changes

Type safety is most valuable when the contract follows the actual path of data. In Core, a controller action receives the application context and the validated request shape. Caller lets a TypeScript client describe and consume HTTP operations through its schemas and request builders. App can use that client in page loaders and components. When the server changes an input, an output, or a route, the surrounding TypeScript code has a shared representation to update against.

Compile-time types and runtime validation serve different jobs. TypeScript helps catch mismatches while code is being developed. A configured schema checks untrusted data at runtime. A type annotation alone does not authorize a user, guarantee a database transaction, or confirm that an email reached an inbox. Those guarantees still belong to the code and services that implement them. Keeping that distinction clear makes the system easier to trust and the examples easier to apply safely.

The same principle applies to shared interfaces. Common defines contracts that different parts of an application can implement. Logger accepts structured context and exposes familiar levels through Igniter’s own manager. Telemetry defines event registries and transport behavior. The application can choose which events matter, which attributes are safe to retain, and where they should be sent. Packages can cooperate without forcing every project to share one global configuration or a single implementation choice.

## Follow the shape of the work

The package boundaries reflect a way to build features without hiding the moving parts. Core defines the request and its context. A domain package can handle a concern such as jobs, files, email, or bot messages. Caller connects another TypeScript client to an HTTP API. The App package can place that client inside a React application. Shared contracts let packages accept application-owned implementations when a project needs a different logger or schema validator.

For example, a user sign-up flow might validate a request in a Core mutation, persist a user through the application’s database, dispatch a welcome message through Jobs, and send it with Mail. Telemetry can record selected lifecycle events, while Logger gives operators useful structured output. Each part has a named API and can be configured or replaced on its own.

This structure also gives coding agents a more useful unit of work. A task can point to a controller, job definition, collection, or connector and the package guide that defines its contract. The agent can inspect adjacent code and follow the same patterns. The developer can review changes at those boundaries instead of untangling a one-off architecture after every prompt.

That does not make generated code automatically correct. Types can catch incompatible values; configured schemas can validate data at runtime; tests and review still determine whether the behavior is right for a product. Authentication policy, data ownership, operational limits, and deployment choices remain application decisions. Igniter.js gives teams a consistent way to make those decisions visible in code.

## AI support that stays close to the repository

Igniter.js is designed for teams that use coding agents as part of development. Clear builders and package boundaries make source easier to inspect. Package documentation provides task-specific guidance. The CLI handles repeatable scaffolding and generation. The MCP packages make development context and application actions available through the Model Context Protocol, depending on which integration a project chooses.

There are two distinct MCP paths. `@igniter-js/mcp-server` runs locally for project-oriented tools such as documentation, analysis, GitHub, memory, and agent delegation. `@igniter-js/adapter-mcp-server` connects an Igniter router to MCP clients by mapping application actions to tools. The first helps an agent work with a codebase; the second lets a client interact with an application API.

The local server is a development tool, separate from the library catalog above. Review its [toolset and runtime guidance](/docs/mcp-server-cli) before enabling it: some analysis and delegation paths currently write diagnostic output to stdout, which can interrupt an MCP STDIO session. Disable those toolsets for STDIO clients until that output is redirected.

Keep the developer in the loop. Give an agent a concrete task, let it use the project’s conventions, inspect the diff, and run the checks that matter to the change. That workflow is more useful than treating a prompt as a substitute for product judgment. Igniter.js aims to make the collaboration legible: what the code does, which package owns it, and where to verify the behavior.

## Pick a first step

You can begin with Core alone and add packages as the product calls for them. If you already have an API, start with Caller. If you are building a React client for an Igniter API, connect it through App. If the next feature needs background work, files, content collections, email, bots, or external integrations, install that package and follow its focused guide.

For a new project, make the first milestone small: create one route, validate one request, and return one typed response. Once that contract is useful, connect a client and let the UI consume it. Add a queue when work needs to outlive the request, or a storage package when files need their own scopes and policies. This keeps the architecture connected to real product needs. Each added package brings its own setup, runtime requirements, and operational decisions, so review its installation and advanced guides before treating an example as a production configuration. The package API reference is the place to check exact exports and supported options when the application moves beyond its first working path.

Use the [Core quick start](/docs/core/quick-start) for a first API. Then browse the package pages above for examples and current APIs. If you are starting a new project, the initializer gives you a guided route from a project name to a starter and selected capabilities.

The direction is simple: make the important boundaries explicit, keep the tools composable, and let developers use AI without giving up control of the system they are building. Igniter.js v1 brings that approach into one TypeScript ecosystem—ready to grow one feature, one package, and one reviewed change at a time.
