## Overview

`@igniter-js/logger` is a **Pino-backed structured logger** with a builder-pattern API. It wraps Pino's raw performance in a clean, TypeScript-first interface that feels at home in the Igniter.js ecosystem.

You configure a logger once with the builder — log level, app name, component, context, and transports — and get a typed manager. No Pino configuration files are required; use a raw Pino target or external transport when you need JSON-line output.

<Callout type="info">
  Logger delegates internally to **Pino v9** — the fastest Node.js logger. You get Pino's performance and ecosystem (pino-pretty, pino/file, external transports) behind a clean Igniter.js API.
</Callout>

### Key Features

- **Builder Pattern** — `.create().withLevel().addTransport().build()` — chained configuration with full TypeScript inference
- **Six Log Levels** — `fatal`, `error`, `warn`, `info`, `debug`, `trace` — plus `success` for positive outcomes
- **Three Built-in Transports** — console (`pino-pretty`), file (`pino/file`), and HTTP (asynchronous batch delivery)
- **External Transports** — use any pino-compatible transport (Logtail, Datadog, Loki, etc.)
- **Child Loggers** — create scoped loggers with merged context for services, requests, or tenants
- **Structured Context** — merge default context into every log entry; add per-call context inline
- **Visual Hierarchy** — `group()`/`groupEnd()` indent log output; `separator()` draws dividers
- **Runtime Control** — change the Pino log level at runtime; app name and component are configured when the logger is built
- **Non-blocking HTTP** — asynchronous batching transport with periodic and worker-close delivery attempts; failed sends are retained in memory between attempts

## Architecture

Logger follows the **Igniter.js builder pattern**: a chainable builder produces a manager around a Pino instance. Builder methods return new builder instances; manager methods such as `setLevel()`, `setAppName()`, and `setComponent()` update the built manager.

```
┌─────────────────────────┐
│  IgniterLoggerBuilder   │  ← Chainable configuration
│  .withLevel()           │
│  .withAppName()         │
│  .withComponent()       │
│  .withContext()         │
│  .addTransport() × N    │
│  .build()               │
└───────────┬─────────────┘
            │ produces
┌───────────▼─────────────┐
│ IgniterLoggerManager    │  ← Built runtime manager
│  .info(msg)             │
│  .error(msg, err)       │
│  .child(name, ctx)      │
│  .group() / .groupEnd() │
│  .separator()           │
│  .setLevel()            │
│  .flush()               │
└───────────┬─────────────┘
            │ delegates to
┌───────────▼─────────────┐
│       Pino v9           │  ← Raw logging engine
│  ┌──────┐ ┌──────┐      │
│  │console│ │ file │ ...  │  ← Transport targets
│  └──────┘ └──────┘      │
└─────────────────────────┘
```

### Transport Resolution

When you call `.addTransport()`, the builder stores a transport configuration. At `.build()` time, each transport is resolved:

| Target | Resolver | Pino Target |
|--------|----------|-------------|
| `"console"` | `resolveConsoleTransport` | `pino-pretty` |
| `"file"` | `resolveFileTransport` | `pino/file` |
| `"http"` | `resolveHttpTransport` | Custom async HTTP worker |
| `(any string)` | Passed through as-is | External pino transport |

If no transports are configured, a **console transport with pretty formatting** is added automatically.

## Quick Start

<Tabs items={['npm', 'pnpm', 'yarn', 'bun']} groupId="package-manager">
  <Tab value="npm">
    ```bash
    npm install @igniter-js/logger
    ```
  </Tab>
  <Tab value="pnpm">
    ```bash
    pnpm add @igniter-js/logger
    ```
  </Tab>
  <Tab value="yarn">
    ```bash
    yarn add @igniter-js/logger
    ```
  </Tab>
  <Tab value="bun">
    ```bash
    bun add @igniter-js/logger
    ```
  </Tab>
</Tabs>

```typescript
import { IgniterLogger } from '@igniter-js/logger';

const logger = IgniterLogger.create().build();

logger.info('Server started on port 3000');
logger.error('Connection failed', new Error('timeout'));
logger.success('Deployment complete');
```

That's it. One import, one builder call, and you're logging. The default setup gives you pretty console output with timestamps.

## Real-World Use Cases

| Scenario | What Logger Provides |
|----------|---------------------|
| **API Server** | Console transport for development, file transport for audit logs, HTTP transport for centralized log ingestion |
| **Microservices** | App name and component labels track which service produced each log; application helpers can require tenant context |
| **CLI Tools** | `success()` for positive outcomes, `group()` for indented progress, `separator()` for section breaks |
| **Background Jobs** | File transport for job logs; use `flush()` during graceful shutdown to drain buffered output |
| **Multi-tenant SaaS** | Use `.child(tenantId, { tenantId })` to add tenant context to child log entries while sharing the configured output |
| **Serverless Functions** | Minimal cold-start overhead; HTTP transport ships logs to external aggregator before function terminates |
