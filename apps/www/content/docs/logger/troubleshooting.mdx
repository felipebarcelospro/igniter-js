## Troubleshooting

Common issues and how to fix them when working with `@igniter-js/logger`.

---

## Debug Messages Not Appearing

**Symptom:** You call `logger.debug(...)` or `logger.trace(...)` but nothing appears in the output.

**Cause:** The log level is set higher than `Debug`. Logger filters out messages below the configured minimum level.

**Solution:** Set the level to `Debug` or `Trace`:

```typescript
// In the builder
const logger = IgniterLogger.create()
  .withLevel(IgniterLogLevel.Debug)
  .build();

// Or at runtime
logger.setLevel(IgniterLogLevel.Debug);
```

<Callout type="info">
  The default level (when not set) is `info` — which means `debug` and `trace` are suppressed by default.
</Callout>

---

## File Transport Not Writing

**Symptom:** You configured a file transport but no file is created or the file is empty.

**Causes and Solutions:**

### 1. Missing flush before exit

File transport buffers output. Without `flush()`, logs may not be written before the process exits:

```typescript
process.on('beforeExit', async () => {
  await logger.flush();
});
```

### 2. Invalid file path

Ensure the directory exists or `mkdir: true` is set:

```typescript
.addTransport({
  target: 'file',
  options: {
    path: './logs/app.log',
    mkdir: true,  // creates ./logs/ if missing
  },
})
```

### 3. Permission denied

Check write permissions on the target directory:

```bash
ls -la ./logs/
# drwxr-xr-x  ... logs/
```

### 4. Verify the file

Add a small delay after logging and flush to confirm:

```typescript
logger.info('Test message');
await logger.flush();
await new Promise(r => setTimeout(r, 100));

import { readFileSync } from 'fs';
console.log(readFileSync('./logs/app.log', 'utf-8'));
```

## HTTP Transport Not Sending

**Symptom:** HTTP transport is configured but logs are not reaching the remote endpoint.

**Causes and Solutions:**

### 1. Batch not yet full

By default, HTTP transport batches 10 entries before sending. Log more entries or lower the `batchSize`:

```typescript
.addTransport({
  target: 'http',
  options: {
    url: 'https://logs.example.com/ingest',
    batchSize: 1,   // send every entry immediately
    flushInterval: 1000,  // or flush every 1s
  },
})
```

### 2. Missing flush on exit

The HTTP transport uses `setInterval` with `.unref()` — it won't keep the process alive. `logger.flush()` flushes Pino's stream, not the HTTP worker's in-memory batch. The worker makes delivery attempts on its threshold, interval, and close:

```typescript
process.on('SIGTERM', async () => {
  await logger.flush(); // Drains Pino's stream; it does not force an HTTP send.
  process.exit(0);
});
```

### 3. Network errors

The HTTP sender puts a failed batch back into its in-memory buffer, but it does not schedule a retry immediately. A later timer or batch flush can send it again; buffered entries are lost if the process exits first. Check your URL, headers, and network:

```typescript
// Verify the endpoint independently
fetch('https://logs.example.com/ingest', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'X-API-Key': '...' },
  body: JSON.stringify({ logs: [], timestamp: new Date().toISOString() }),
}).then(r => console.log('Status:', r.status));
```

### 4. Firewall / CORS

If your log endpoint is behind a firewall, ensure the process has outbound access to the URL.

## Need JSON Lines Instead of Pretty Console Output

The built-in `console` target always resolves to `pino-pretty`; setting `pretty: false` does not switch it to raw JSON. Use a Pino-compatible raw output target or an external transport when a log collector requires JSON lines. The `colorize` option only controls ANSI colors; it does not change the output format.

## `flush()` Hangs or Times Out

**Symptom:** `await logger.flush()` never resolves.

**Cause:** Pino's flush callback may be waiting on a slow output stream. This callback does not wait for the HTTP sender's network request.

**Solution:** Add a timeout:

```typescript
const flushWithTimeout = async (logger: IIgniterLoggerManager, ms = 5000) => {
  await Promise.race([
    logger.flush(),
    new Promise((_, reject) =>
      setTimeout(() => reject(new Error('Flush timed out')), ms)
    ),
  ]);
};

process.on('SIGTERM', async () => {
  try {
    await flushWithTimeout(logger, 3000);
  } catch {
    console.error('Flush timed out — exiting anyway');
  }
  process.exit(0);
});
```

## Child Logger Doesn't Inherit Parent Context

**Symptom:** A child logger isn't picking up the parent's default context.

**Cause:** Child loggers inherit context from the **Pino base object** (set at `.build()` time), not from the builder state directly. If the parent logger was built without `.withContext()`, children won't have it.

**Solution:** Ensure parent context is configured in the builder before `.build()`:

```typescript
// ✅ Context is in the builder — child inherits it
const logger = IgniterLogger.create()
  .withContext({ service: 'api' })
  .build();

const child = logger.child('http');
child.info('Request');  // includes service=api
```

---

## `defineScopes<T>()` Does Not Constrain `child()`

The current public `IIgniterLoggerManager.child()` signature accepts an optional `Record<string, unknown> | string` context. `defineScopes<T>()` changes the builder generic but is not reflected in that method signature. If an application requires particular context fields, enforce them in a typed helper around `logger.child()`.

## `group()` / `groupEnd()` Mismatch

**Symptom:** Indentation is wrong — logs are permanently indented or not indented at all.

**Cause:** `group()` and `groupEnd()` calls are unbalanced — more `group()` calls than `groupEnd()` (or vice versa).

**Solution:** Ensure every `group()` has a matching `groupEnd()`:

```typescript
logger.group('Section');

try {
  // ... work ...
} finally {
  logger.groupEnd();  // always end, even on error
}
```

## Pino Version Conflicts

**Symptom:** `Error: Cannot find module 'pino'` or version mismatch errors.

**Cause:** Multiple Pino versions in your dependency tree.

**Solution:** Check for duplicate Pino installations:

```bash
npm ls pino
# or
pnpm why pino
```

Logger requires Pino v9 (`"pino": "^9.0.0"`). If another package depends on Pino v8, use `overrides` or `resolutions`:

```json title="package.json"
{
  "overrides": {
    "pino": "^9.0.0"
  }
}
```
