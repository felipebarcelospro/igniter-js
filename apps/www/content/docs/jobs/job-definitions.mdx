Job definitions are built using the `IgniterQueue` builder. You create queues, register jobs (with handlers, schemas, and hooks), and optionally add cron tasks — all with full TypeScript type inference.

## Creating a Queue

Use `IgniterQueue.create(name)` to start a new queue builder:

```typescript
import { IgniterQueue } from '@igniter-js/jobs'

const queue = IgniterQueue.create('email')
```

The queue name is used as the namespace for dispatching jobs: `jobs.email.sendWelcome.dispatch(...)`.

---

## Adding Jobs

Call `.addJob(name, definition)` on the queue builder to register a job:

```typescript
import { z } from 'zod'

const emailQueue = IgniterQueue.create('email')
  .addJob('sendWelcome', {
    input: z.object({
      email: z.string().email(),
      name: z.string(),
    }),
    handler: async ({ input, context, job }) => {
      console.log(`Sending welcome email to ${input.email}`)
      await context.mailer.sendWelcome(input.email, input.name)
      return { sent: true, timestamp: new Date() }
    },
  })
  .build()
```

### Job Definition Properties

| Property | Type | Required | Description |
|----------|------|----------|-------------|
| `handler` | `(ctx) => Promise<TResult> \| TResult` | **Yes** | The function that executes when the job runs |
| `input` | `IgniterJobsSchema` | No | Schema for input validation (Zod, Standard Schema v1) |
| `output` | `IgniterJobsSchema` | No | Schema for output validation |
| `onStart` | `(ctx) => void \| Promise<void>` | No | Called when job execution begins |
| `onSuccess` | `(ctx) => void \| Promise<void>` | No | Called when job completes successfully |
| `onFailure` | `(ctx) => void \| Promise<void>` | No | Called when job fails |
| `onProgress` | `(ctx) => void \| Promise<void>` | No | Called when the job reports progress |
| `stream` | `IgniterJobsJobStreamDefinition` | No | Typed per-job event stream configuration |
| `queue` | `string` | No | Optional child queue override (adapter-dependent) |

Plus all [dispatch options](#dispatch-options) can be set as defaults on the job definition.

## The Handler Context

The handler receives an execution context with everything it needs:

```typescript
interface IgniterJobsExecutionContext<TContext, TInput, TStreamEvents> {
  input: InferInput<TInput>        // Validated input (fully typed)
  context: TContext                // Your application context
  job: {
    id: string                     // Unique job identifier
    name: string                   // Job name (e.g., 'sendWelcome')
    queue: string                  // Queue name
    attemptsMade: number           // How many times this job has run
    createdAt?: Date               // When the job was created
    metadata?: Record<string, unknown>
    updateProgress?: (progress: number, message?: string) => Promise<void>
    stream: IgniterJobsExecutionStreamEmitter  // Typed stream emitter
  }
  scope?: IgniterJobsScopeEntry    // Scope info if dispatched from a scoped instance
}
```

### Context Type Inference

The context type is inferred from `withContext()` on the main builder — no explicit generics needed:

```typescript
const jobs = IgniterJobs.create()
  .withContext(async () => ({
    db: new PrismaClient(),
    mailer: new Mailer(),
  }))
  // TContext = { db: PrismaClient; mailer: Mailer }
  .addQueue(emailQueue)
  .build()

// Inside the handler:
// context.db   → PrismaClient (fully typed)
// context.mailer → Mailer (fully typed)
```

## Input Validation

Jobs automatically validate their input against the provided schema. Invalid input causes the job to fail before the handler executes:

```typescript
const processOrderQueue = IgniterQueue.create('orders')
  .addJob('process', {
    input: z.object({
      orderId: z.string().uuid(),
      amount: z.number().positive(),
      currency: z.enum(['USD', 'EUR', 'GBP']),
    }),
    handler: async ({ input }) => {
      // input.orderId is typed as string
      // input.amount is typed as number (> 0)
      // input.currency is typed as 'USD' | 'EUR' | 'GBP'
      console.log(`Processing order ${input.orderId}`)
    },
  })
  .build()

// ✅ Valid — job executes
await jobs.orders.process.dispatch({
  input: { orderId: '123e4567-e89b-12d3-a456-426614174000', amount: 99.99, currency: 'USD' },
})

// ❌ Invalid — throws JOBS_INPUT_VALIDATION_FAILED
await jobs.orders.process.dispatch({
  input: { orderId: 'not-a-uuid', amount: -10, currency: 'JPY' },
})
```

### Supported Schema Libraries

The `input` and `output` fields support:

- **Zod** schemas (with `_input`/`_output` and `parse`/`safeParse`)
- **Standard Schema v1** compatible schemas
- **Any object** with `parse()` and optional `safeParse()`

<Callout type="info" title="Output Validation">
  The `output` schema validates the handler's return value. If validation fails, the job is marked as failed with a `JOBS_OUTPUT_VALIDATION_FAILED` error.
</Callout>

## Lifecycle Hooks

React to job lifecycle events without modifying the handler:

```typescript
const trackedJob = IgniterQueue.create('analytics')
  .addJob('track', {
    input: z.object({ event: z.string(), userId: z.string() }),
    handler: async ({ input, context }) => {
      await context.analytics.track(input.event, input.userId)
      return { tracked: true }
    },

    onStart: async ({ input, job }) => {
      console.log(`Job ${job.name} (${job.id}) started`)
    },

    onProgress: async ({ job, progress, message }) => {
      console.log(`Job ${job.id} progress: ${progress}% — ${message}`)
    },

    onSuccess: async ({ input, job, result, duration }) => {
      console.log(`Job ${job.name} completed in ${duration}ms`)
      await context.metrics.record('job.success', { duration })
    },

    onFailure: async ({ input, job, error, isFinalAttempt }) => {
      console.error(`Job ${job.name} failed:`, error.message)
      if (isFinalAttempt) {
        await context.alerts.send({
          type: 'critical',
          message: `Job ${job.name} failed after all retries`,
        })
      }
    },
  })
  .build()
```

### Hook Context

Each hook receives a typed context:

| Hook | Additional Properties |
|------|-----------------------|
| `onStart` | `startedAt` |
| `onProgress` | `progress: number`, `message?: string` |
| `onSuccess` | `result: TResult`, `duration?: number` |
| `onFailure` | `error: Error`, `isFinalAttempt: boolean` |

<Callout type="info" title="Hook Execution">
  Hooks execute asynchronously and errors in hooks **do not fail the job**. Use hooks for logging, metrics, and notifications — not critical business logic.
</Callout>

## Dispatch Options

All dispatch options can be set as **defaults** on the job definition or **overridden** at dispatch time:

```typescript
const queue = IgniterQueue.create('email')
  .addJob('sendWelcome', {
    // Job defaults (applied to every dispatch)
    attempts: 3,
    priority: 5,
    removeOnComplete: 100,
    removeOnFail: 50,

    handler: async ({ input }) => {
      await sendEmail(input.email)
    },
  })
  .build()

// Override defaults at dispatch time
await jobs.email.sendWelcome.dispatch({
  input: { email: 'urgent@example.com', name: 'VIP' },
  priority: 10,     // Override default priority
  attempts: 5,      // Override default attempts
  delay: 0,         // Send immediately
})
```

### Available Dispatch Options

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `input` | `TInput` | **Required** | Validated input payload |
| `jobId` | `string` | Auto-generated | Custom job identifier |
| `priority` | `number` | — | Higher = processed first |
| `delay` | `number` | 0 | Delay in milliseconds before execution |
| `attempts` | `number` | — | Maximum execution attempts |
| `removeOnComplete` | `boolean \| number` | — | Auto-remove completed jobs (or keep N) |
| `removeOnFail` | `boolean \| number` | — | Auto-remove failed jobs (or keep N) |
| `metadata` | `Record<string, unknown>` | — | Custom metadata for search/filtering |
| `limiter` | `{ max, duration }` | — | Per-job rate limiter |
| `scope` | `IgniterJobsScopeEntry` | — | Scope entry for multi-tenant isolation |

## Queue-Level Defaults

Apply defaults to all jobs in a queue using `.withQueueDefaults()` on the main builder:

```typescript
const jobs = IgniterJobs.create()
  .withAdapter(...)
  .withService('my-api')
  .withEnvironment('production')
  .withContext(async () => ({ db }))
  .withQueueDefaults({
    attempts: 3,
    removeOnComplete: 200,
    removeOnFail: 100,
  })
  .addQueue(emailQueue)
  .addQueue(analyticsQueue)
  .build()
// All jobs inherit these defaults unless overridden
```

## Multiple Queues Pattern

Organize jobs into separate queues by domain:

```typescript
// src/jobs/email.queue.ts
export const emailQueue = IgniterQueue.create('email')
  .addJob('sendWelcome', { /* ... */ })
  .addJob('sendPasswordReset', { /* ... */ })
  .build()

// src/jobs/payment.queue.ts
export const paymentQueue = IgniterQueue.create('payment')
  .addJob('processPayment', { /* ... */ })
  .addJob('refundPayment', { /* ... */ })
  .build()

// src/jobs/analytics.queue.ts
export const analyticsQueue = IgniterQueue.create('analytics')
  .addJob('trackEvent', { /* ... */ })
  .addJob('generateReport', { /* ... */ })
  .build()

// src/services/jobs.ts
const jobs = IgniterJobs.create()
  .withAdapter(...)
  .withService('my-api')
  .withEnvironment('production')
  .withContext(async () => ({ db, mailer, paymentService }))
  .addQueue(emailQueue)
  .addQueue(paymentQueue)
  .addQueue(analyticsQueue)
  .build()

// Dispatch from any queue
await jobs.email.sendWelcome.dispatch({ ... })
await jobs.payment.processPayment.dispatch({ ... })
await jobs.analytics.trackEvent.dispatch({ ... })
```

## Real-World Examples

### Email Notification Job with Retry

```typescript
const emailQueue = IgniterQueue.create('email')
  .addJob('sendNotification', {
    input: z.object({
      to: z.string().email(),
      subject: z.string().min(1),
      body: z.string(),
    }),
    attempts: 3,
    handler: async ({ input, context }) => {
      const result = await context.mailer.send(input)
      if (!result.success) {
        throw new Error(`Mail send failed: ${result.error}`)
      }
      return { messageId: result.id }
    },
    onFailure: async ({ job, error, isFinalAttempt }) => {
      if (isFinalAttempt) {
        await context.notifications.sendSlack({
          text: `Failed to send email to ${input.to}: ${error.message}`,
        })
      }
    },
  })
  .build()
```

### Order Processing with Database Transaction

```typescript
const orderQueue = IgniterQueue.create('orders')
  .addJob('process', {
    input: z.object({
      orderId: z.string(),
      items: z.array(z.object({
        productId: z.string(),
        quantity: z.number().positive(),
      })),
    }),
    handler: async ({ input, context }) => {
      return await context.db.$transaction(async (tx) => {
        const order = await tx.order.update({
          where: { id: input.orderId },
          data: { status: 'PROCESSING' },
        })

        for (const item of input.items) {
          await tx.inventory.decrement({
            where: { productId: item.productId },
            data: { quantity: item.quantity },
          })
        }

        await tx.order.update({
          where: { id: input.orderId },
          data: { status: 'COMPLETED' },
        })

        return { orderId: order.id, processed: true }
      })
    },
  })
  .build()
```

### File Processing with Progress

```typescript
const mediaQueue = IgniterQueue.create('media')
  .addJob('processImage', {
    input: z.object({
      fileId: z.string(),
      operations: z.array(z.enum(['resize', 'optimize', 'watermark'])),
    }),
    handler: async ({ input, job, context }) => {
      const file = await context.storage.get(input.fileId)

      for (let i = 0; i < input.operations.length; i++) {
        const op = input.operations[i]
        await context.imageProcessor[op](file)
        await job.updateProgress(
          Math.round(((i + 1) / input.operations.length) * 100),
          `Completed ${op}`
        )
      }

      return { processed: true, fileId: input.fileId }
    },
  })
  .build()
```

## Best Practices

- **Use descriptive queue names** — queue names appear in logs, metrics, and monitoring tools
- **Validate input strictly** — use Zod's full validation power (`.email()`, `.url()`, `.min()`, `.max()`)
- **Keep handlers focused** — each job should do one thing well; compose jobs for complex workflows
- **Use context for dependencies** — access services through context, not global state
- **Set reasonable attempts** — 3 retries is a good starting point; adjust based on failure patterns
- **Use hooks for observability** — log, track metrics, and alert from hooks, not inside handlers
- **Separate queues by domain** — email, payment, analytics queues let you scale and monitor independently
