Beyond basic job execution, Igniter.js Jobs provides typed job streams, event subscriptions, telemetry integration, and multiple adapter backends. This page covers the advanced features that make the jobs system production-ready.

## Typed Job Streams

Job streams enable per-job, real-time event streaming — emit typed events during job execution, subscribe to live updates, and read persisted event history.

### Defining Stream Events

Define typed stream events on a job definition:

```typescript
import { z } from 'zod'

const aiQueue = IgniterQueue.create('ai')
  .addJob('generate', {
    input: z.object({ prompt: z.string() }),
    stream: {
      persistence: { enabled: true, maxEvents: 100 },
      events: {
        'text-delta': z.string(),
        'status': z.object({ phase: z.string() }),
        'done': z.object({ chunks: z.number() }),
      },
    },
    handler: async ({ input, job }) => {
      // Emit typed stream events during execution
      await job.stream.emit('status', { phase: 'thinking' })
      await job.stream.emit('text-delta', 'Hello, ')
      await job.stream.emit('text-delta', 'world!')
      await job.stream.emit('done', { chunks: 2 })

      return { ok: true }
    },
  })
  .build()
```

### Stream Configuration

| Option | Type | Description |
|--------|------|-------------|
| `persistence.enabled` | `boolean` | Enable persisted event history |
| `persistence.maxEvents` | `number` | Maximum events to retain |
| `events` | `Record<string, Schema>` | Typed event schema map |

### Emitting Events

Inside the handler, use `job.stream.emit(type, data)`:

```typescript
handler: async ({ job }) => {
  await job.stream.emit('status', { phase: 'processing' })
  // TypeScript validates: type must be 'text-delta' | 'status' | 'done'
  // data must match the schema for that event type
}
```

With untyped streams (no `events` schema), you can emit any string type with any data:

```typescript
stream: { persistence: { enabled: false } },
handler: async ({ job }) => {
  await job.stream.emit('custom-event', { any: 'data' })
  // type: string, data: unknown
}
```

### Subscribing to Live Events

```typescript
const job = jobs.ai.generate.get('job_abc123')

const unsubscribe = await job.stream().subscribe((event) => {
  // Fully typed discriminated union:
  if (event.type === 'text-delta') {
    console.log(event.data) // string
  } else if (event.type === 'status') {
    console.log(event.data.phase) // string
  } else if (event.type === 'done') {
    console.log(event.data.chunks) // number
  }
})

// Later: await unsubscribe()
```

### Reading Persisted History

```typescript
const history = await jobs.ai.generate.get('job_abc123').stream().read({
  after: 'event_cursor_123', // Pagination cursor (optional)
  limit: 50,                  // Max events (optional)
})

console.log(history.items)     // Typed event array
console.log(history.hasMore)   // boolean
console.log(history.nextCursor) // string | undefined
```

If `persistence.enabled` is `false`, `read()` returns an empty array.

<Callout type="info" title="Stream Use Cases">
  Job streams are perfect for:
  - **AI/LLM pipelines** — stream token deltas, status updates, and completion events
  - **File processing** — emit progress, chunk info, and final results
  - **Data pipelines** — stream ETL stages, row counts, and validation results
  - **User notifications** — push real-time updates to clients via WebSocket/SSE
</Callout>

## Event Subscriptions

Subscribe to job lifecycle events at multiple levels:

### Global Subscription

```typescript
const unsubscribe = await jobs.subscribe((event) => {
  console.log(`[${event.type}]`, event.data)
  // Events include: enqueued, started, completed, failed, etc.
})

// Later
await unsubscribe()
```

### Per-Job Subscription

```typescript
const unsubscribe = await jobs.email.sendWelcome.subscribe((event) => {
  console.log(`sendWelcome: ${event.type}`)
})
```

### Per-Queue Subscription

```typescript
const unsubscribe = await jobs.email.subscribe((event) => {
  console.log(`Email queue event: ${event.type}`)
})
```

### Event Shape

```typescript
interface IgniterJobsEvent {
  type: string           // Event type (e.g., 'igniter.jobs.job.completed')
  data: unknown          // Event payload
  timestamp: Date        // When the event occurred
  scope?: {              // Scope info (if scoped)
    type: string
    id: string | number
    tags?: Record<string, unknown>
  }
}
```

## Telemetry Integration

Integrate with `@igniter-js/telemetry` for structured observability:

```typescript
import { IgniterTelemetry } from '@igniter-js/telemetry'
import { IgniterJobsTelemetryEvents } from '@igniter-js/jobs/telemetry'

const telemetry = IgniterTelemetry.create()
  .withService('my-api')
  .withEnvironment('production')
  .addEvents(IgniterJobsTelemetryEvents)
  .build()

const jobs = IgniterJobs.create()
  .withAdapter(IgniterJobsBullMQAdapter.create({ redis }))
  .withService('my-api')
  .withEnvironment('production')
  .withContext(async () => ({ db }))
  .withTelemetry(telemetry)
  .addQueue(emailQueue)
  .build()
```

The jobs runtime automatically emits telemetry events for:
- Job enqueued, started, completed, and failed
- Worker lifecycle changes

## Adapters

Igniter.js Jobs ships with three adapters, importable from specific subpaths:

### BullMQ Adapter (Production)

For Redis-backed production deployments:

```typescript
import { IgniterJobsBullMQAdapter } from '@igniter-js/jobs/adapters/node'
import { Redis } from 'ioredis'

const redis = new Redis(process.env.REDIS_URL)

const jobs = IgniterJobs.create()
  .withAdapter(IgniterJobsBullMQAdapter.create({ redis }))
  // ...
  .build()
```

**Requirements:** `@igniter-js/adapter-bullmq`, `bullmq`, `ioredis` (all peer dependencies)

### Bun SQLite Adapter

For standalone deployments without Redis — ideal for single-server apps:

```typescript
import { IgniterJobsBunSQLiteAdapter } from '@igniter-js/jobs/adapters/bun'

const jobs = IgniterJobs.create()
  .withAdapter(IgniterJobsBunSQLiteAdapter.create({
    path: './data/jobs.db',
    durable: true,              // Immediate persistence
    heartbeatInterval: 10_000,  // Worker heartbeat (default: 10000)
    pollTimeout: 0,             // Long-poll timeout (default: 0)
    batchSize: 10,              // Jobs per worker batch (default: 10)
    lockDuration: 30_000,       // Active job lock (default: 30000)
    maxStalledCount: 1,         // Max stalled before fail (default: 1)
  }))
  // ...
  .build()
```

**Requirements:** Bun runtime only

### In-Memory Adapter (Dev/Test)

For development and testing — no external dependencies:

```typescript
import { IgniterJobsMemoryAdapter } from '@igniter-js/jobs/adapters/mock'

const jobs = IgniterJobs.create()
  .withAdapter(IgniterJobsMemoryAdapter.create())
  // ...
  .build()
```

**Requirements:** None — fully self-contained

### Adapter Comparison

| Feature | BullMQ | Bun SQLite | Memory |
|---------|--------|------------|--------|
| Persistence | Redis | SQLite file | In-memory only |
| Distributed workers | Yes | No (single process) | No (single process) |
| Dashboard/monitoring | Bull Board | Custom | Custom |
| Production-ready | Yes | Yes (single server) | No (dev/test only) |
| Setup complexity | Medium (Redis) | Low (file) | None |
| Import path | `adapters/node` | `adapters/bun` | `adapters/mock` |

## Logger Integration

Attach a custom logger to capture internal events:

```typescript
import type { IgniterLogger } from '@igniter-js/jobs'

const logger: IgniterLogger = {
  info: (message, meta) => console.log(`[INFO] ${message}`, meta),
  warn: (message, meta) => console.warn(`[WARN] ${message}`, meta),
  error: (message, meta) => console.error(`[ERROR] ${message}`, meta),
}

const jobs = IgniterJobs.create()
  .withLogger(logger)
  // ...
  .build()
```

## Real-World Patterns

### AI Pipeline with Streams

```typescript
const aiQueue = IgniterQueue.create('ai')
  .addJob('generate', {
    input: z.object({ prompt: z.string() }),
    stream: {
      persistence: { enabled: true, maxEvents: 200 },
      events: {
        'token': z.string(),
        'tool-call': z.object({ name: z.string(), args: z.record(z.unknown()) }),
        'done': z.object({ text: z.string(), tokens: z.number() }),
      },
    },
    handler: async ({ input, job, context }) => {
      const stream = await context.llm.stream(input.prompt)

      let text = ''
      let tokens = 0

      for await (const chunk of stream) {
        if (chunk.type === 'token') {
          await job.stream.emit('token', chunk.text)
          text += chunk.text
          tokens++
        } else if (chunk.type === 'tool-call') {
          await job.stream.emit('tool-call', chunk.tool)
        }
      }

      await job.stream.emit('done', { text, tokens })
      return { text, tokens }
    },
  })
  .build()
```

### WebSocket Streaming to Client

```typescript
// Server-side: subscribe to job stream, forward to WebSocket
async function streamJobToClient(ws: WebSocket, jobId: string) {
  const unsubscribe = await jobs.ai.generate
    .get(jobId)
    .stream()
    .subscribe((event) => {
      ws.send(JSON.stringify(event))
    })

  ws.on('close', async () => {
    await unsubscribe()
  })
}
```

### Custom Retry Logic with Hooks

```typescript
const resilientQueue = IgniterQueue.create('api')
  .addJob('sync', {
    input: z.object({ endpoint: z.string().url() }),
    attempts: 5,
    handler: async ({ input }) => {
      const response = await fetch(input.endpoint)
      if (!response.ok) {
        throw new Error(`HTTP ${response.status}: ${response.statusText}`)
      }
      return response.json()
    },
    onFailure: async ({ input, job, error, isFinalAttempt }) => {
      if (isFinalAttempt) {
        await alerts.send({
          message: `Sync job failed after ${job.attemptsMade} attempts: ${error.message}`,
        })
      }
    },
  })
  .build()
```

## Best Practices

### General
- **Use typed streams** — define event schemas for compile-time safety in AI/streaming pipelines
- **Enable stream persistence** only when you need history — it adds storage overhead
- **Set appropriate adapter** — BullMQ for distributed, Bun SQLite for single-server, Memory for tests
- **Integrate telemetry** — production observability from day one
- **Use scopes** — isolate tenants with `addScope({ required: true })` in multi-tenant apps

### Error Handling
- **Use lifecycle hooks** for logging and alerts, not business logic
- **Set `attempts`** on job definitions — don't rely on infinite retries
- **Monitor failure rates** — use `jobs.search('jobs', { status: 'failed' })` periodically
- **Handle shutdown** — always call `jobs.shutdown()` before process exit

### Performance
- **Match concurrency to workload** — CPU: 2–5, I/O: 10–50, Database: 5–10
- **Use rate limiters** for downstream API calls — prevent 429 errors
- **Clean completed jobs** — prevent Redis memory bloat with `queue.get().clean()`
- **Separate queues by domain** — independent scaling and monitoring

## Troubleshooting

### Stream Events Not Persisting

**Problem**: `stream().read()` returns empty when `persistence.enabled` is `true`.

**Solutions**:
- Verify `persistence.enabled: true` is set in the stream config
- Ensure the adapter supports stream persistence (Memory adapter supports it)
- Check `maxEvents` — if exceeded, old events may be evicted

### Telemetry Events Not Emitting

**Problem**: No telemetry events despite calling `withTelemetry()`.

**Solutions**:
- Verify the telemetry instance was built with `IgniterJobsTelemetryEvents`
- Check `service` and `environment` match between telemetry and jobs config
- Ensure the telemetry instance is correctly configured

### Adapter Import Errors

**Problem**: TypeScript can't resolve adapter imports.

**Solutions**:
- BullMQ: `import { IgniterJobsBullMQAdapter } from '@igniter-js/jobs/adapters/node'`
- Bun SQLite: `import { IgniterJobsBunSQLiteAdapter } from '@igniter-js/jobs/adapters/bun'`
- Memory: `import { IgniterJobsMemoryAdapter } from '@igniter-js/jobs/adapters/mock'`

### Scope Required Errors

**Problem**: `JOBS_SCOPE_REQUIRED` error on dispatch.

**Solution**: Use `jobs.scope('type', 'id')` before dispatching, or set `required: false` on the scope definition.
