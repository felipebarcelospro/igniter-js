Workers are the processes that execute your background jobs. They continuously poll the backend (Redis, SQLite, or memory) for new jobs and execute them according to your configuration.

## The Worker Builder

Workers are created through the fluent builder at `jobs.worker.create()`:

```typescript
const worker = await jobs.worker.create()
  .addQueue('email')
  .withConcurrency(5)
  .onActive(({ job }) => {
    console.log(`Processing: ${job.name} (${job.id})`)
  })
  .onSuccess(({ job, result }) => {
    console.log(`Completed: ${job.name}`)
  })
  .onFailure(({ job, error }) => {
    console.error(`Failed: ${job.name} — ${error.message}`)
  })
  .start()

console.log(`Worker started: ${worker.id}`)
```

### Worker Builder Methods

| Method | Description |
|--------|-------------|
| `.addQueue(name)` | Add a queue for this worker to process |
| `.withConcurrency(n)` | Set maximum concurrent job executions |
| `.withLimiter(limiter)` | Apply a rate limiter to this worker |
| `.onActive(handler)` | Called when a job starts processing |
| `.onSuccess(handler)` | Called when a job completes successfully |
| `.onFailure(handler)` | Called when a job fails |
| `.onIdle(handler)` | Called when no jobs are available |
| `.start()` | Build and start the worker (returns `Promise<WorkerHandle>`) |

## Auto-Start Workers

For simpler setups, configure workers to start automatically when the jobs runtime is built:

```typescript
const jobs = IgniterJobs.create()
  .withAdapter(IgniterJobsBullMQAdapter.create({ redis }))
  .withService('my-api')
  .withEnvironment('production')
  .withContext(async () => ({ db, mailer }))
  .addQueue(emailQueue)
  .addQueue(analyticsQueue)
  .withAutoStartWorker({
    queues: ['email', 'analytics'],
    concurrency: 5,
  })
  .build()
// Workers start automatically — no manual start() needed
```

### Auto-Start Options

| Option | Type | Description |
|--------|------|-------------|
| `queues` | `string[]` | Queue names to process |
| `concurrency` | `number` | Concurrent job limit |
| `limiter` | `{ max, duration }` | Rate limiter configuration |

## Worker-Level Defaults

Apply default worker configuration across all workers via `withWorkerDefaults()`:

```typescript
const jobs = IgniterJobs.create()
  .withAdapter(...)
  .withService('my-api')
  .withEnvironment('production')
  .withContext(async () => ({ db }))
  .withWorkerDefaults({
    concurrency: 5,
  })
  .addQueue(emailQueue)
  .addQueue(analyticsQueue)
  .build()
```

## Concurrency Control

Control how many jobs run simultaneously per worker:

```typescript
// CPU-intensive jobs — low concurrency
const cpuWorker = await jobs.worker.create()
  .addQueue('image-processing')
  .withConcurrency(2)
  .start()

// I/O-bound jobs — high concurrency
const ioWorker = await jobs.worker.create()
  .addQueue('email')
  .addQueue('notifications')
  .withConcurrency(50)
  .start()

// Critical jobs — one at a time
const criticalWorker = await jobs.worker.create()
  .addQueue('payment')
  .withConcurrency(1)
  .start()
```

<Callout type="info" title="Choosing Concurrency">
  - **CPU-intensive**: 2–5 to avoid contention
  - **I/O-bound**: 10–50 to maximize throughput
  - **Database-heavy**: 5–10 to avoid pool exhaustion
  - **Critical/ordered**: 1 for sequential processing
</Callout>

## Rate Limiters

Apply rate limiters to control throughput at the worker level:

```typescript
const worker = await jobs.worker.create()
  .addQueue('email')
  .withConcurrency(5)
  .withLimiter({
    max: 100,        // Maximum jobs
    duration: 60_000, // Per 60 seconds (1 minute)
  })
  .start()
// Processes at most 100 jobs per minute
```

Rate limiters can also be set per-job through the [dispatch options](/docs/jobs/job-definitions#available-dispatch-options).

## Lifecycle Event Handlers

React to worker lifecycle events with typed handlers:

### onActive

Called when a job starts processing:

```typescript
.onActive(({ job }) => {
  console.log(`[${job.queue}] Processing ${job.name} (${job.id})`)
  metrics.increment('jobs.active', { queue: job.queue })
})
```

### onSuccess

Called when a job completes successfully:

```typescript
.onSuccess(({ job, result }) => {
  console.log(`[${job.queue}] Completed ${job.name} in ${Date.now() - job.createdAt.getTime()}ms`)
  metrics.increment('jobs.completed', { queue: job.queue })
})
```

### onFailure

Called when a job fails:

```typescript
.onFailure(({ job, error }) => {
  console.error(`[${job.queue}] Failed ${job.name}: ${error.message}`)
  metrics.increment('jobs.failed', { queue: job.queue })

  if (job.attemptsMade >= 3) {
    alerts.send({ type: 'critical', message: `Job exhausted retries: ${job.name}` })
  }
})
```

### onIdle

Called when no jobs are available:

```typescript
.onIdle(() => {
  console.log('Worker idle — no jobs in queue')
})
```

### Handler Context

| Handler | Context Properties |
|---------|-------------------|
| `onActive` | `job: IgniterJobSearchResult` |
| `onSuccess` | `job: IgniterJobSearchResult`, `result: unknown` |
| `onFailure` | `job: IgniterJobSearchResult`, `error: Error` |
| `onIdle` | _(none)_ |

## Multiple Workers

Run multiple workers for the same queue (horizontal scaling) or different queues (isolation):

```typescript
// Two workers sharing the email queue (horizontal scaling)
const emailWorker1 = await jobs.worker.create()
  .addQueue('email').withConcurrency(5).start()

const emailWorker2 = await jobs.worker.create()
  .addQueue('email').withConcurrency(5).start()

// Dedicated worker for critical queue
const paymentWorker = await jobs.worker.create()
  .addQueue('payment').withConcurrency(1)
  .onFailure(({ job, error }) => {
    alerts.send({ type: 'critical', message: `Payment job failed: ${job.name}` })
  })
  .start()
```

Multiple workers on the same queue automatically share the workload — think of it as horizontal scaling for job processing.

## Worker Handle

The `WorkerHandle` returned by `.start()` gives you runtime control:

```typescript
const worker = await jobs.worker.create()
  .addQueue('email')
  .start()

// Inspect state
console.log(worker.id)           // Unique worker ID
console.log(worker.queues)       // ['email']
console.log(worker.isRunning())  // true
console.log(worker.isPaused())   // false

// Control lifecycle
await worker.pause()             // Stop processing new jobs
await worker.resume()            // Resume processing
console.log(worker.isPaused())   // true

// Get metrics
const metrics = await worker.getMetrics()
console.log(metrics.processed)   // Number of jobs processed
console.log(metrics.failed)      // Number of failed jobs
console.log(metrics.avgDuration) // Average job duration in ms
console.log(metrics.concurrency) // Current concurrency
console.log(metrics.uptime)      // Uptime in milliseconds

// Shut down
await worker.close()
console.log(worker.isClosed())   // true
```

## Graceful Shutdown

Always shut down workers gracefully before your application exits:

```typescript
// Shut down all workers and close adapter connections
await jobs.shutdown()

// Or close individual workers
await worker.close()
```

In production, handle OS signals:

```typescript
process.on('SIGTERM', async () => {
  console.log('SIGTERM received — shutting down gracefully...')
  await jobs.shutdown()
  process.exit(0)
})

process.on('SIGINT', async () => {
  console.log('SIGINT received — shutting down...')
  await jobs.shutdown()
  process.exit(0)
})
```

<Callout type="warn" title="Graceful Shutdown Matters">
  Always call `shutdown()` before exiting. This ensures:
  - In-flight jobs complete or are properly requeued
  - Redis/SQLite connections are closed cleanly
  - No jobs are lost during the shutdown window
</Callout>

## Real-World Patterns

### Priority-Based Workers

Run separate workers for different priority levels:

```typescript
// High-priority worker — immediate processing, low concurrency
const highPriorityWorker = await jobs.worker.create()
  .addQueue('priority-high')
  .withConcurrency(1)
  .onFailure(({ job, error }) => {
    alerts.send({ type: 'critical', message: `High-priority job failed: ${job.name}` })
  })
  .start()

// Normal worker — standard processing
const normalWorker = await jobs.worker.create()
  .addQueue('default')
  .withConcurrency(10)
  .start()
```

### Monitoring with Metrics

```typescript
const worker = await jobs.worker.create()
  .addQueue('email')
  .withConcurrency(10)
  .onActive(({ job }) => {
    prometheus.activeJobs.inc({ queue: job.queue })
  })
  .onSuccess(({ job }) => {
    prometheus.activeJobs.dec({ queue: job.queue })
    prometheus.completedJobs.inc({ queue: job.queue })
  })
  .onFailure(({ job }) => {
    prometheus.activeJobs.dec({ queue: job.queue })
    prometheus.failedJobs.inc({ queue: job.queue })
  })
  .start()
```

## Best Practices

- **Set appropriate concurrency** — match to your workload type
- **Use rate limiters** — protect downstream services from being overwhelmed
- **Handle shutdown gracefully** — always call `shutdown()` or `close()`
- **Monitor worker health** — track processed, failed, and active job counts
- **Separate workers by priority** — critical jobs get dedicated low-concurrency workers
- **Scale horizontally** — run multiple workers on the same queue for redundancy

## Troubleshooting

### Workers Not Processing

**Problem**: Jobs are queued but not executing.

**Solutions**:
- Verify the worker's `addQueue('email')` matches the queue name exactly
- Check that `start()` was called (auto-start or manual)
- Verify Redis/SQLite connectivity
- Check for unhandled errors in the worker initialization

### High Memory Usage

**Problem**: Worker consumes too much memory.

**Solutions**:
- Reduce concurrency — fewer concurrent jobs means less memory
- Check for memory leaks in job handlers (accumulating arrays, unclosed connections)
- Monitor per-job memory usage

### Worker Crashes

**Problem**: Worker crashes unexpectedly.

**Solutions**:
- Add error handling in lifecycle hooks — hooks throwing errors shouldn't crash the worker
- Use a process manager (PM2, systemd) to restart crashed workers
- Monitor logs for unhandled rejections
