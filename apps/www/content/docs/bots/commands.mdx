## Commands

Commands are the primary way users interact with your bot. The framework resolves names and aliases, routes raw command parameters to handlers, supports flat command groups, and passes registered commands to adapters that support platform registration.

---

## Basic Command

Every command requires: `name`, `aliases`, `description`, `help`, and a `handle` function:

```typescript
builder.addCommand('start', {
  name: 'start',
  aliases: ['hello', 'hi'],
  description: 'Greets the user',
  help: 'Use /start to receive a welcome message',
  async handle(ctx) {
    await ctx.reply(`👋 Welcome, ${ctx.message.author.name}!`);
  },
});
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | `string` | ✅ | Command name without slash. Must not contain `/` or spaces. |
| `aliases` | `string[]` | ✅ | Alternative names. Each must follow the same rules. |
| `description` | `string` | ✅ | Short description (used for platform registration). |
| `help` | `string` | ✅ | Detailed help shown on invalid usage. |
| `args` | `ZodType<TArgs>` | ❌ | Type-level command argument declaration. The runtime does not parse or validate this schema. |
| `handle` | `(ctx, params) => Promise<void>` | ✅ | Receives the raw `params` from the normalized command message. |
| `subcommands` | `Record<string, ...>` | ❌ | Declared in the type, but nested subcommands are not dispatched by the current runtime. Use flat command groups. |

<Callout type="info">
  `Bot.command()` validates the command definition and name when you create it. Builder methods such as `addCommand()` store the object under a key; they do not run that validation helper for you.
</Callout>

## Aliases

Aliases let users trigger the same command with different names. All aliases are converted to lowercase and indexed for O(1) lookup:

```typescript
builder.addCommand('help', {
  name: 'help',
  aliases: ['commands', '?', 'h'], // /help, /commands, /?, /h all work
  description: 'Show available commands',
  help: 'Use /help to see available commands',
  async handle(ctx) { /* ... */ },
});
```

## Validate Command Input

Handlers receive the normalized message's raw `params` array. The optional `args` property is part of the command type, but the runtime does not parse it, validate incoming arguments, or pass a parsed object to `handle`. Validate parameters in the handler:

```typescript
import { z } from 'zod';

builder.addCommand('search', {
  name: 'search',
  aliases: ['find', 's'],
  description: 'Search the catalog',
  help: 'Use /search &lt;query&gt; [category] to find items',
  async handle(ctx, params) {
    const parsed = z.object({
      query: z.string().min(2),
      category: z.enum(['books', 'movies', 'music']).optional(),
    }).safeParse({ query: params[0], category: params[1] });

    if (!parsed.success) {
      await ctx.reply('Use /search <query> [books|movies|music].');
      return;
    }

    const { query, category } = parsed.data;
    const results = await searchCatalog(query, category);

    if (results.length === 0) {
      await ctx.reply(`No results found for "${query}".`);
      return;
    }

    await ctx.reply(
      `🔍 Found **${results.length}** result(s) for "${query}":\n\n` +
      results.map((r, i) => `${i + 1}. ${r.title}`).join('\n'),
    );
  },
});
```

<Callout type="info">
  `params` comes from the adapter's normalized command message. Tokenization and quoting behavior can differ by platform; treat user input as untrusted and validate it in your handler. The runtime does not automatically use `BotCommand.args`.
</Callout>

## Nested Subcommands

`BotCommand` currently declares a `subcommands` property in its TypeScript type, but the message-processing runtime does not dispatch nested commands. Use `addCommandGroup()` to register flat, prefixed commands instead.

<Callout type="warn">
  Do not rely on `subcommands` to execute handlers. A message such as `/admin ban 123` is dispatched as the top-level `admin` command with remaining tokens in `params`.
</Callout>

## Command Groups

Group related commands with a common prefix using `.addCommandGroup()`:

```typescript
builder.addCommandGroup('admin', {
  ban: {
    name: 'ban',
    aliases: ['block'],
    description: 'Ban a user',
    help: 'Use /admin_ban &lt;user_id&gt;',
    async handle(ctx) { /* ... */ },
  },
  kick: {
    name: 'kick',
    aliases: ['remove'],
    description: 'Kick a user',
    help: 'Use /admin_kick &lt;user_id&gt;',
    async handle(ctx) { /* ... */ },
  },
  stats: {
    name: 'stats',
    aliases: [],
    description: 'Admin statistics',
    help: 'Use /admin_stats for statistics',
    async handle(ctx) { /* ... */ },
  },
});

// Results in commands: /admin_ban, /admin_kick, /admin_stats
```

Command groups create **flat, prefixed commands** such as `/admin_ban`. The registered command names and aliases are resolved like other top-level commands.

## Multiple Command Registration

Register several commands at once:

```typescript
builder.addCommands({
  start: { name: 'start', aliases: ['hello'], /* ... */ },
  help: { name: 'help', aliases: ['?'], /* ... */ },
  about: { name: 'about', aliases: ['info'], /* ... */ },
  contact: { name: 'contact', aliases: ['support'], /* ... */ },
});
```

## Dynamic Registration at Runtime

Commands can be added after the bot is built:

```typescript
const bot = builder.build();

// Later, dynamically register a new command
bot.registerCommand('maintenance', {
  name: 'maintenance',
  aliases: ['maint'],
  description: 'Toggle maintenance mode',
  help: 'Use /maintenance on|off',
  async handle(ctx) {
    const isMaintenance = await toggleMaintenance();
    await ctx.reply(`Maintenance mode: ${isMaintenance ? 'ON' : 'OFF'}`);
  },
});
```

This is useful for plugin systems, hot-reload during development, or commands that depend on runtime state.

## Platform Auto-Registration

Commands are automatically registered with platforms that support it:

- **Telegram** — Commands are set via `setMyCommands` during `init()` when `webhook.url` is configured. Without that URL, adapter initialization returns before command registration.
- **Discord** — Slash commands are registered globally through the Applications API during `init()`
- **WhatsApp** — Commands are handled entirely by the framework (no native command system)

<Callout type="info">
  The current adapter registers commands at the application level. It does not provide a guild-specific registration option.
</Callout>

## Creating Commands in Separate Files

Use `Bot.command()` to create a command definition in a separate file. `Bot` is exported from the package root:

```typescript
// commands/start.ts
import { Bot } from '@igniter-js/bot';

export const startCommand = Bot.command({
  name: 'start',
  aliases: ['hello', 'hi'],
  description: 'Greets the user',
  help: 'Use /start to receive a welcome message',
  async handle(ctx) {
    await ctx.reply('👋 Welcome!');
  },
});

// lib/bot.ts
import { startCommand } from './commands/start';

const bot = IgniterBot.create()
  .addCommand('start', startCommand)
  .build();
```

`Bot.command()` validates required fields and command-name constraints at creation time. It does not validate handler input.

## Best Practices

- ✅ **Use descriptive names** — `search` is better than `s`. Aliases handle shortcuts.
- ✅ **Always provide help text** — The framework uses the command's help text when a handler reports invalid usage; it does not implement a special `/command --help` flag.
- ✅ **Validate user input in the handler** — Parse the raw `params` array with Zod or another validator before using it.
- ✅ **Organize related commands with groups** — Keeps your bot configuration readable.
- ✅ **Keep handlers focused** — Extract business logic into separate functions for testability.
- ❌ **Don't assume nested `subcommands` are dispatched** — Use flat command groups for related commands.
- ❌ **Don't hardcode platform-specific logic** — Use `ctx.provider` to check the current platform only when truly needed.
