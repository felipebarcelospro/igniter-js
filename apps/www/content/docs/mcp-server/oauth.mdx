## How authentication works

The adapter can wrap its request handler with mcp-handler bearer-token validation. Provide an issuer and a <code>verifyToken</code> callback that returns MCP <code>AuthInfo</code> for a valid token or <code>undefined</code> for an invalid token. The callback must return the access token, client ID, and scopes; arbitrary fields such as <code>valid</code> and <code>user</code> are not part of <code>AuthInfo</code>.

The adapter does not automatically copy the authenticated user into <code>McpContext.context</code>. If tool handlers need user-specific context, create it in your router's request context factory from the incoming request, using your application's own authentication rules.

<Callout type="warn" title="Verification is required to enforce authentication">
  The <code>verifyToken</code> option is optional in the type. The adapter only enables the auth wrapper when both OAuth options and <code>verifyToken</code> are supplied. Setting only <code>issuer</code> does not protect tool requests.
</Callout>

## Configure token verification

Return the <code>AuthInfo</code> shape defined by the MCP SDK. Map the fields to claims from your validated token:

~~~typescript
import { IgniterMcpServer } from '@igniter-js/adapter-mcp-server';
import { AppRouter } from '@/igniter.router';

const { handler, auth } = IgniterMcpServer
  .create()
  .router(AppRouter)
  .withOAuth({
    issuer: process.env.OAUTH_ISSUER!,
    scopes: ['mcp:read'],
    verifyToken: async ({ bearerToken }) => {
      if (!bearerToken) return undefined;

      const claims = await verifyAccessToken(bearerToken);
      if (!claims) return undefined;

      return {
        token: bearerToken,
        clientId: claims.clientId,
        scopes: claims.scopes,
        expiresAt: claims.expiresAt,
        extra: { subject: claims.subject },
      };
    },
  })
  .build();

export const GET = handler;
export const POST = handler;
export const OPTIONS = auth.cors;
~~~

<code>verifyAccessToken</code> is application code: it must validate signature, issuer, audience, expiry, and any other claims your system requires. Return <code>undefined</code> when validation fails.

## Resource metadata endpoint

The adapter returns a resource metadata handler as <code>auth.resource</code>; it does not install a framework route for you. Expose it at the path configured in <code>resourceMetadataPath</code> and allow the metadata CORS preflight:

~~~typescript
// src/app/.well-known/oauth-protected-resource/route.ts
import { auth } from '@/app/api/mcp/[...transport]/route';

export const GET = auth.resource;
export const OPTIONS = auth.cors;
~~~

The current adapter fallback for <code>resourceMetadataPath</code> is <code>well-known/oauth-authorization-server</code>. Set an explicit path in <code>withOAuth</code> when your deployment uses a different metadata route.

## Function API

The function API uses the same options and callback contract:

~~~typescript
const { server, auth } = createMcpAdapter({
  router: AppRouter,
  oauth: {
    issuer: process.env.OAUTH_ISSUER!,
    resourceMetadataPath: '/.well-known/oauth-protected-resource',
    scopes: ['mcp:read'],
    verifyToken: async ({ bearerToken }) => {
      if (!bearerToken) return undefined;
      const claims = await verifyAccessToken(bearerToken);
      if (!claims) return undefined;
      return {
        token: bearerToken,
        clientId: claims.clientId,
        scopes: claims.scopes,
        expiresAt: claims.expiresAt,
        extra: { subject: claims.subject },
      };
    },
  },
});

export const GET = server;
export const POST = server;
export const OPTIONS = auth.cors;
~~~

## Scopes and application authorization

The adapter passes configured <code>scopes</code> to the auth middleware as required scopes. Your verifier should return the scopes granted to the token. Enforce user- and resource-level access in your application; a valid bearer token alone does not authorize every router action.

Do not assume <code>AuthInfo.extra</code> is copied to tool handler context. Build any user-specific context explicitly in your router's context factory, or perform authorization inside the action using verified application context.
