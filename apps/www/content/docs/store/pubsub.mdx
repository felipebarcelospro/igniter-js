## Overview

`@igniter-js/store` provides a fully typed Pub/Sub system with two complementary APIs:

1. **String-based API** — `store.events.publish("user:created", payload)`, `store.events.subscribe("user:created", handler)`
2. **Proxy-based API** — `store.events.user.created.publish(payload)`, `store.events.user.created.subscribe(handler)`

Both are powered by the same typed event registry, giving you full TypeScript inference for payloads and event names.

<Callout type="info">
  Events are scoped to your store instance. If you use scoped stores (`store.scope(...)`), published events and subscriptions are also scoped — each tenant gets isolated channels.
</Callout>

---

## Defining Typed Events

Use `IgniterStoreEvents` to define event schemas per feature module. Each feature exports its own events definition, which you combine in the store builder.

```typescript
import { z } from "zod";
import { IgniterStoreEvents } from "@igniter-js/store";

// src/features/user/user.events.ts
export const UserEvents = IgniterStoreEvents
  .create("user")
  .event("created", z.object({
    userId: z.string(),
    email: z.string().email(),
    createdAt: z.string(),
  }))
  .event("deleted", z.object({
    userId: z.string(),
    deletedAt: z.string(),
  }))
  .build();
```

### Nested Groups

Organize related events under groups:

```typescript
export const OrderEvents = IgniterStoreEvents
  .create("order")
  .event("placed", z.object({
    orderId: z.string(),
    total: z.number(),
  }))
  .group("fulfillment", (group) =>
    group
      .event("shipped", z.object({
        orderId: z.string(),
        trackingId: z.string(),
      }))
      .event("delivered", z.object({
        orderId: z.string(),
        deliveredAt: z.string(),
      }))
  )
  .group("payments", (group) =>
    group
      .event("authorized", z.object({
        orderId: z.string(),
        amount: z.number(),
      }))
      .event("refunded", z.object({
        orderId: z.string(),
        refundId: z.string(),
      }))
  )
  .build();
```

### Registering Events with the Store

```typescript
import { IgniterStore } from "@igniter-js/store";
import { UserEvents } from "./features/user/user.events";
import { OrderEvents } from "./features/order/order.events";

const store = IgniterStore.create()
  .withAdapter(adapter)
  .withService("api")
  .addEvents(UserEvents)
  .addEvents(OrderEvents)
  .build();
```

<Callout type="warn">
  Each namespace must be **unique** — calling `addEvents()` with the same namespace twice throws `STORE_DUPLICATE_NAMESPACE`.
</Callout>

## String-Based API

The string-based API uses colon-separated event names (`namespace:eventName`).

### Publishing

```typescript
// Fully typed — TypeScript knows the payload shape
await store.events.publish("user:created", {
  userId: "123",
  email: "avery@example.com",
  createdAt: new Date().toISOString(),
});

// Nested group event
await store.events.publish("order:fulfillment:shipped", {
  orderId: "o_456",
  trackingId: "TRK-789",
});
```

### Subscribing

The handler receives an `IgniterStoreEventContext` with `type`, `data`, `timestamp`, and optional `scope`:

```typescript
const unsubscribe = await store.events.subscribe("user:created", (ctx) => {
  console.log(ctx.type);      // "user:created"
  console.log(ctx.data);      // { userId: "123", email: "avery@example.com", ... }
  console.log(ctx.timestamp); // "2026-06-02T..."
  console.log(ctx.scope);     // undefined (or { key: "organization", identifier: "org_1" } if scoped)
});

// Later: stop listening
await unsubscribe();
```

### Wildcard Subscriptions

Subscribe to all events in a namespace using `*`:

```typescript
// Listen to all user events
await store.events.subscribe("user:*", (ctx) => {
  // ctx.type is "user:created" | "user:deleted"
  // ctx.data is the union of all user event payloads
  switch (ctx.type) {
    case "user:created":
      console.log("New user:", ctx.data.email);
      break;
    case "user:deleted":
      console.log("User deleted:", ctx.data.userId);
      break;
  }
});

// Listen to everything
await store.events.subscribe("*", (ctx) => {
  console.log(`[${ctx.type}]`, ctx.data);
});
```

## Proxy-Based API

The proxy API provides auto-completing access to typed events:

```typescript
// Publishing — fully typed, no string literals
await store.events.user.created.publish({
  userId: "123",
  email: "avery@example.com",
  createdAt: new Date().toISOString(),
});

// Nested groups
await store.events.order.fulfillment.shipped.publish({
  orderId: "o_456",
  trackingId: "TRK-789",
});

// Subscribing
const unsub = await store.events.user.created.subscribe((ctx) => {
  console.log(ctx.data.email); // Fully typed — no casting needed
});

await unsub();
```

<Callout type="success" title="Best Practice">
  Use the **proxy API** for individual event subscriptions (best DX with auto-complete), and the **string API** for wildcard subscriptions or dynamic event names.
</Callout>

## Event Context Envelope

Every handler receives an `IgniterStoreEventContext`:

| Field | Type | Description |
|-------|------|-------------|
| `type` | `string` | Full event name (e.g., `"user:created"`) |
| `data` | `TPayload` | The event payload (typed from schema) |
| `timestamp` | `string` | ISO 8601 timestamp when published |
| `scope` | `object?` | Current scope info if scoped store is used |

## Schema Validation

### Configuring Validation

Validation is configured per `addEvents()` call:

```typescript
const store = IgniterStore.create()
  .withAdapter(adapter)
  .withService("api")
  .addEvents(UserEvents, {
    validatePublish: true,     // Validate payloads when publishing (default: true)
    validateSubscribe: false,  // Validate received payloads (default: false)
    throwOnValidationError: true, // Throw on invalid payloads (default: true)
  })
  .build();
```

### Validation Behavior

```typescript
// ✅ Valid payload — succeeds
await store.events.publish("user:created", {
  userId: "123",
  email: "avery@example.com",
  createdAt: new Date().toISOString(),
});

// ❌ Invalid payload — throws STORE_SCHEMA_VALIDATION_FAILED
await store.events.publish("user:created", {
  userId: 123,        // Should be string
  email: "invalid",   // Not an email format
});
```

## Real-World Patterns

### Cross-Service Communication

```typescript
// Service A: Order placed
await store.events.publish("order:placed", {
  orderId: "o_123",
  userId: "u_456",
  total: 99.99,
  items: [{ productId: "p_1", quantity: 2 }],
});

// Service B: Send confirmation
await store.events.subscribe("order:placed", async (ctx) => {
  await emailService.sendConfirmation(ctx.data.userId, ctx.data.orderId);
});

// Service C: Update inventory
await store.events.subscribe("order:placed", async (ctx) => {
  for (const item of ctx.data.items) {
    await inventoryService.decrement(item.productId, item.quantity);
  }
});
```

### Cache Invalidation via Events

```typescript
// After database write, emit invalidation event
await db.user.update({ where: { id: userId }, data });
await store.events.publish("cache:invalidate:user", { userId });

// Cache layer listens and purges
await store.events.subscribe("cache:invalidate:user", async (ctx) => {
  await store.kv.remove(`user:${ctx.data.userId}`);
  await store.kv.remove("users:list");
});
```

### Activity Feed

```typescript
const ActivityEvents = IgniterStoreEvents
  .create("activity")
  .event("user_action", z.object({
    userId: z.string(),
    action: z.string(),
    metadata: z.record(z.unknown()).optional(),
  }))
  .build();

// Publish user actions
await store.events.activity.user_action.publish({
  userId: "u_123",
  action: "page_viewed",
  metadata: { page: "/dashboard", referrer: "/home" },
});

// Activity feed listener
await store.events.activity.user_action.subscribe(async (ctx) => {
  await db.activity.create({
    data: {
      userId: ctx.data.userId,
      action: ctx.data.action,
      metadata: ctx.data.metadata,
      createdAt: new Date(ctx.timestamp),
    },
  });
});
```

## Best Practices

### ✅ Organize Events by Feature

```typescript
// ✅ Good — one events file per feature
// features/user/user.events.ts
export const UserEvents = IgniterStoreEvents.create("user")...build();

// features/order/order.events.ts
export const OrderEvents = IgniterStoreEvents.create("order")...build();

// features/payment/payment.events.ts
export const PaymentEvents = IgniterStoreEvents.create("payment")...build();

// src/store.ts — combine them all
const store = IgniterStore.create()
  .addEvents(UserEvents)
  .addEvents(OrderEvents)
  .addEvents(PaymentEvents)
  .build();
```

### ❌ Don't Define Everything in One Place

```typescript
// ❌ Bad — monolithic, hard to maintain
const AllEvents = IgniterStoreEvents
  .create("all")
  .event("user:created", userSchema)
  .event("order:placed", orderSchema)
  .event("payment:authorized", paymentSchema)
  .build();
```

### ✅ Handle Errors in Subscribers

```typescript
await store.events.subscribe("order:placed", async (ctx) => {
  try {
    await processOrder(ctx.data);
  } catch (error) {
    console.error(`Failed to process order ${ctx.data.orderId}:`, error);
    // Don't let one failure break the subscription
  }
});
```

## Limitations

- **Wildcards in Redis**: The built-in Redis adapter uses `SUBSCRIBE` (exact channels), not `PSUBSCRIBE` (patterns). Wildcard matching is handled in TypeScript types only — for true Redis pattern subscriptions, implement a custom adapter. Use explicit channel names in production.
- **No at-least-once delivery**: Pub/Sub is fire-and-forget. For guaranteed delivery, use [Redis Streams](/docs/store/streams) with consumer groups.
