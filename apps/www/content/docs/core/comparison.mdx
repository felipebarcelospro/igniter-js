# Comparing backend approaches

Igniter.js combines a TypeScript HTTP API framework with optional packages for calling, jobs, storage, collections, and integrations. The right choice depends on the boundaries and conventions your application needs; this page focuses on those choices rather than ranking frameworks with universal feature claims.

## Where Igniter.js fits

Choose Igniter.js when you want to define HTTP actions in TypeScript, infer their input and output types, and add focused backend capabilities from the Igniter.js package ecosystem. Core can be used with supported framework adapters or as a request handler, while packages such as Caller and Jobs are installed separately.

- [Core quick start](/docs/core/quick-start) introduces the builder and a first route.
- [Core adapters](/docs/core/adapters) lists the framework adapters shipped by Core.
- [Caller](/docs/caller) covers typed calls from client and server code.
- [Jobs](/docs/jobs) covers background work and queue adapters.

## Comparing common choices

| If your priority is… | Consider… | What to evaluate |
| --- | --- | --- |
| A general-purpose Node.js HTTP server with a large middleware ecosystem | Express or Fastify | Whether you want to assemble routing, validation, and client typing from separate libraries. |
| End-to-end typed procedure calls in a TypeScript application | tRPC | Whether an RPC-shaped API matches your clients and deployment boundaries. |
| React server functions tied to one full-stack framework | Next.js Server Actions | Whether your API needs to serve non-React clients or be deployed independently. |
| Typed HTTP actions plus optional packages for backend capabilities | Igniter.js | Whether its action model, adapters, and package APIs fit your application. |

These approaches solve overlapping but different problems. Their performance, OpenAPI support, framework compatibility, and operational features depend on versions and configuration, so compare the current project documentation and a representative prototype before deciding.

## A practical evaluation checklist

1. Define the clients that must call your API (web, mobile, external services, or server-side code).
2. Check whether you need conventional HTTP routes, RPC procedures, or framework-bound server functions.
3. Verify the framework adapters and runtimes you plan to deploy.
4. Prototype validation, error handling, testing, and observability with your actual dependencies.
5. Measure the workload that matters to your application instead of relying on generic benchmark claims.
